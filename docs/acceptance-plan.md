# PortQueue 验收计划

## 1. 验收环境

- Windows。
- SQL Server Developer 或 Express，数据库名 `PortQueue`。
- VS Code、.NET 8 SDK、Node.js LTS。
- 浏览器使用本机前端开发服务器或后端托管的静态页面。

## 2. 中期检查目标

2026-11-11 中期检查按教师通知准备三分钟以内 PPT，展示已完成的数据库结构、数据和系统界面。本项目以单人开发为基准，中期交付范围如下；课程最终完整功能要求仍在后续阶段落实。

1. SQL 脚本可以从空数据库恢复表、约束和核心视图。
2. 预约查询完成 SQL Server、Dapper、API 和 Vue 的真实只读链路，支持筛选、分页和异常状态。
3. 数据库层业务过程与核心规则有可复核的验证证据；保留已有完整路径测试，说明它与完整页面联调的区别。
4. 展示一次泊位时间窗重叠被拒绝、相接允许的规则对照，并能说明事务与历史版本的作用。
5. 保存真实页面截图、查询结果和 review；PPT 约 165 秒，11 月 10 日冻结功能并演练。

详细实现和用例见 [阶段 2 预约查询](stages/stage-2-appointment-query.md)。预约登记、审核、队列、计划和执行页面在最终系统验收中完成，不作为本次中期的全部前置条件。

## 3. 系统验收案例

### A 正常锚地路径

创建船舶和本港到访，提交预约并审核；登记进入锚地，查看有效队列和进入时间；确认泊位计划；登记实际进港、靠泊、离泊；查看完整时间线和统计结果。

### B 直接靠泊路径

对不需要等待的已批准预约直接创建和确认泊位计划，不写锚地排队记录；事件视图仍能得到进港、靠泊和离泊的完整路径。

### C 泊位冲突

先确认泊位 A 的 10:00—12:00 计划，再尝试确认 11:00—13:00 的第二个计划。系统拒绝第二次确认并说明同泊位时间窗冲突；把第二个计划改为 12:00—14:00 后允许确认。

### D 计划版本

已确认计划调整时间时生成新版本；新版本冲突则原当前版本不变。靠泊后再修改计划离泊时间，历史靠泊偏差仍以靠泊前最后确认的适用版本计算。

### E 队列与实际在场

登记两艘船进入同一锚地，人工调序并填写原因；取消一艘尚未离锚的预约，确认它退出有效队列但仍计入在场数量；登记离锚后才从在场数量中移除。

### F 参照完整性

尝试保存不存在的船公司、字典项或泊位；尝试使用非 `SHIP_TYPE` 字典项；尝试给同一泊位重复加入同一船型。三类操作都必须失败，且不能留下部分记录。

### G 并发与重复提交

两个浏览器同时确认同一泊位的重叠时间窗；最多一个事务成功。重复点击靠泊或离泊按钮不能产生第二条同类事件。

## 4. 数据库验收证据

每个案例保存：输入条件、调用的页面或过程、数据库前后状态、返回消息和截图。报告中至少展示表结构、主外键关系、视图 SQL、核心过程、触发器、索引和一个完整查询结果。

## 5. 交付清单

- `PortQueue.sln` 和后端源代码。
- `web/port-queue-web` 前端源代码和 lockfile。
- `database/` 全部 SQL 脚本及恢复顺序。
- 样例数据、测试脚本和测试报告。
- 环境配置示例，不包含密码。
- 课程设计报告、答辩 PPT 和实际开发工作记录。

## 6. 最终系统完成判定

只有在空数据库恢复、真实页面写入、异常约束、统计查询和连续演示全部通过后，才将系统标记为可验收。仅有静态页面、仅有 Mock 数据或只在单个表中成功保存，不计入闭环完成。
