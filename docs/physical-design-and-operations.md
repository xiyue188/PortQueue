# 数据库物理设计与业务操作设计

## 1. 设计范围

本阶段把逻辑模型转成 SQL Server 的可部署结构，并明确每个跨表操作如何提交。设计范围仍为 21 个基本关系、3 个业务视图和前期定义的五个功能区域。应用层不自动迁移数据库，`database/` 中的脚本是唯一部署来源。

## 2. 物理对象清单

### 2.1 表

`role`、`user_account`、`dictionary_item`、`shipping_company`、`port`、`terminal`、`anchorage`、`berth`、`ship`、`berth_ship_type`、`port_call`、`arrival_appointment`、`anchorage_queue_entry`、`queue_adjustment_record`、`berth_plan`、`berth_plan_revision`、`port_event`、`audit_log`、`anchorage_event_link`、`port_entry_event_link`、`berth_event_link` 共 21 张表，与逻辑模型 R01-R21 对应。

三个事件关联表的主键都是 `event_id`。事件公共表只保存事件本身的公共属性；具体对象由分类表引用。船型代码、船型名称和字典类型通过 `dictionary_item` 查询，不在船舶或泊位适用船型中复制。

### 2.2 索引

- 业务编号候选键：船舶 IMO/MMSI、船公司代码、港口代码、预约编号、用户名、角色名称和字典类型代码。
- 组织范围候选键：码头归属港口＋码头代码、锚地归属港口＋锚地代码、泊位归属码头＋泊位代码、到访船舶＋到访编号、版本计划＋版本号。
- 调度查询：有效锚地的锚地＋状态＋队列序号、泊位版本的泊位＋计划时间、事件时间＋事件类型。
- 部分唯一索引：有效队列同一锚地的序号唯一；每个计划最多一条当前版本。

索引只服务于可解释的查询和约束，不为每个字段建立索引。正式项目阶段使用 SQL Server 执行计划检查列表查询、时间窗冲突查询和统计查询。

## 3. 业务操作契约

所有写操作通过 API 调用 Application 服务，服务再调用对应的数据库过程。过程在数据库内校验状态并启动事务；异常使用业务错误编号返回，API 把它转换为稳定的错误码和中文提示。

| 操作 | 前置条件 | 事务内动作 | 成功结果 | 失败结果 |
|---|---|---|---|---|
| 新建到访和预约 | 船舶在册；时间合法；该到访无预约 | 写入 `port_call`、`arrival_appointment` | 返回到访和预约编号 | 唯一键、时间或船舶状态不合法时整体回滚 |
| 审核预约 | 预约为待审核或按规则重新审核；审核人有效 | 锁定预约，写入审核状态、审核人、时间和意见 | 预约进入已批准或已驳回 | 状态不允许时回滚，不写半条审核记录 |
| 登记进入锚地 | 预约已批准；无未离开停留；锚地可用 | 创建排队记录，计算初始序号，写入进入事件及关联 | 进入有效队列 | 重复进入、锚地不可用或并发冲突时回滚 |
| 调整排队 | 记录处于等待或已安排；新序号有效 | 锁定锚地有效队列，重排受影响记录，写调整快照 | 队列连续、唯一，保留调整原因 | 并发或序号不合法时回滚 |
| 登记离开锚地 | 存在未离开停留；时间晚于进入时间 | 写离开事件，更新排队状态为已离开并释放序号 | 在场查询得到离开时间 | 重复离开或时间倒置时回滚 |
| 创建计划版本 | 预约已批准；时间段合法 | 锁定计划，按计划内版本号递增写入版本 | 新版本形成，草稿不影响当前安排 | 计划已完成或取消时拒绝 |
| 确认泊位计划 | 船型、尺度、吃水、载重吨和泊位适配有效；候选版本属于该计划 | 串行化锁定同泊位有效计划；检查冲突；切换当前版本并写确认信息 | 每个计划一个当前版本，时间窗无冲突 | 任何校验失败全部回滚，原当前版本保留 |
| 登记实际进港 | 预约已批准；该到访尚无实际进港事件 | 写 `PORT_ENTER` 公共事件和 R20 关联 | 业务时间线出现进港事件 | 重复登记时拒绝 |
| 登记靠泊 | 存在当前已确认执行版本；无重复靠泊 | 写靠泊事件和 R21 关联，计划进入执行中 | 固定执行基准版本 | 版本、状态或时间不合规时回滚 |
| 登记离泊 | 已有靠泊；无重复离泊；时间晚于靠泊；使用同一执行基准版本 | 写离泊事件和 R21 关联，计划及预约完成 | 形成最终执行事实 | 时间倒置、基准不一致或重复事件时回滚 |

## 4. 事务和并发

### 4.1 泊位时间窗

确认计划采用 `SERIALIZABLE` 隔离并锁定目标泊位的当前版本。冲突条件为：

```text
existing_start < candidate_end
AND existing_end > candidate_start
```

两个时间段首尾相接时不冲突。确认过程先检查候选版本，再将原当前版本置为非当前，最后将候选版本标记为当前；任何一步失败都回滚。

### 4.2 锚地队列

有效队列只包括 `WAITING` 和 `ASSIGNED`。活动序号必须非空且在同一锚地内唯一；离开或取消后释放序号。计算新序号和调序必须锁定同一锚地的有效记录，避免两个调度员得到同一序号。

### 4.3 事件分类

`ANCHORAGE_ENTER` 和 `ANCHORAGE_LEAVE` 只进入锚地关联；`PORT_ENTER` 只进入进港关联；`BERTHING` 和 `UNBERTHING` 只进入靠离泊关联。过程将公共事件和分类关联放在同一事务中。触发器阻止错误类型和同一事件的重复分类；直接表写入权限在部署时收回，仅保留过程或 API 数据库用户权限。

## 5. 查询视图

- `v_port_event`：沿三条互斥路径返回事件、所属预约和排队或执行版本。
- `v_anchorage_queue`：返回队列、船舶、锚地、进入时间和离开时间；实际时间来自事件关联。
- `v_current_berth_plan`：返回计划当前版本、泊位、计划时间、确认人和船舶。

视图只组织查询，不存储新的事实。等待时长、在泊时长、计划偏差等派生指标由查询时根据事件和计划版本计算。

## 6. 关键业务过程的返回约定

过程成功返回受影响的主键和最新状态；失败抛出 `THROW` 业务错误编号。API 统一返回：

```json
{
  "code": "BERTH_TIME_CONFLICT",
  "message": "目标泊位的有效时间窗存在冲突。",
  "details": { "berthId": 3 }
}
```

错误码不能依赖 SQL Server 的英文异常文本。前端根据错误码展示明确原因，并保留字段级错误位置。

## 7. 仍需在下一阶段完成的实现项

当前脚本已经覆盖表、主要索引、三个视图、字典与事件保护触发器以及五个核心过程。后续数据库实现继续补充通用审计触发器、队列调序过程、计划版本创建过程、权限用户、可重复种子数据和自动化约束测试。补充对象必须先更新本文件和验收用例，再进入 API 联调。
