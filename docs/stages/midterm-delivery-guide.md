## 谁登记，谁审核

第一阶段正式功能报告写明“调度员依据船公司提供的船舶和本港到访信息登记预约”。因此船公司/授权代理提出申请，港口调度员在内部工作台代为录入和提交，审核员审批。系统操作者与申请提出者不是同一个概念。

没有船方自助端；不能把 DISPATCHER 改名为船员就宣称已有船方权限。未来自助端需要明确账号归属、可操作的船舶及申请范围，届时单独设计。当前四角色、数据库关系和授权保持正式模型语义。演示采用调度员提交、审核员审批；管理员可跨职责，但未实现强制禁止同人登记审核规则。

完整模块、术语及时间含义见 [业务流程](../business-flow.md)。本次到访预计时间是船方行程预计，申请时间是进港诉求，泊位时间是港方资源安排，实际时间必须来自实际记录。当前事件模型不单列港界离港，不能把离泊说成已记录驶离港界。

## 输入 → 处理 → 输出示例

选择已有船舶，填写本次到访、未来申请到港/离港、吃水及作业时长 → 调度员保存草稿 → API 从会话取操作者，数据库验证权限、引用、时间和状态，事务保存到访、预约及审计 → 返回预约编号和草稿状态。

修改草稿并提交 → 数据库校验并发版本及申请到港仍在未来 → 变为待审核，草稿不可继续编辑。审核员填写意见并批准或驳回 → 同一事务更新审核人、时间、状态和审计 → 列表、详情、总览局部更新。保存已成功但读取失败时提示刷新，不把成功写入误判为未保存。结果不明先查询，不盲目重复写入。
