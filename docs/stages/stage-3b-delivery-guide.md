# 阶段 3B 交付说明：真实账号快捷登录与预约审核

日期：2026-11-09。范围：演示登录改进、总览图文层次、完整预约详情，以及批准/驳回业务闭环。3C 登记、草稿编辑与提交尚未实施。

## 1. 现在如何登录

打开 http://127.0.0.1:5173，点击左下“登录”，选择账号，再点击“登录”。选择会自动填入用户名与初始密码 `123456`；也可以输入自己的账号。窄屏先展开导航。

| 选项 | 姓名 | 用户名 | 本轮实际可用操作 |
|---|---|---|---|
| 管理员 | 陈宁 | pq.admin | 查询、批准、驳回 |
| 调度员 | 周航 | pq.dispatcher | 查询；登记/提交随 3C 开放 |
| 审核员 | 林悦 | pq.reviewer | 查询、批准、驳回 |
| 记录员 | 许舟 | pq.recorder | 查询；事件录入随后续阶段开放 |

四个账号已在本机开发库建立，无需再次初始化。它们具有真实数据库身份，选择按钮只填写凭据；登录仍校验密码哈希、账号和角色状态，后端决定权限。前端不会自行切换角色。

快捷入口仅在 Development 且 `DemoAccounts:Enabled=true` 时提供。账号停用、变更角色或修改密码后，不再承诺默认密码可用；初始化不会重置这些改动。生产环境不提供快捷列表，也拒绝演示专用账号登录。个人账号密码下限已由 12 位调整为 6 位，上限仍为 128 位。

其他已恢复数据库的开发环境，可先构建 Release，再显式初始化一次：

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet run --project src/PortQueue.Api/PortQueue.Api.csproj --configuration Release --no-build -- account seed-demo
```

该命令只补齐缺失的专用账号，不重置个人账号，不启动第二个 Web 服务。个人账号创建、重置和启停命令沿用 [3A 说明](stage-3a-delivery-guide.md)，密码在终端隐藏输入。账号管理页面不在本轮范围。

## 2. 原来错误提示为什么不准确

原请求校验把各种模型输入统一标成查询错误，而登录界面缺少对格式错误的单独处理，最终把输入问题落入泛化的服务错误反馈。本轮在 HTTP 边界和前端分别处理输入不合法、用户名/密码不匹配、会话令牌变化、限速和真正的连接失败。

例如用户名输入中文会提示允许的字符；密码错误会提示“用户名或密码错误，或账号不可用”，保留用户名并清空错误密码；这些错误不会把账号区变成“服务不可用”。会话变化提供刷新恢复，连接故障才提示检查后端和数据库。

## 3. 页面变化

总览继续表达全港概况，进港预约继续承担清单和具体详情。主图、侧栏、工具区、共同外框与港口动态沿用既定冰蓝风格。正文与字段提高字号，宽屏放宽外框并增大文字，避免大屏中央缩成一块小界面。

总览新增六状态环形分布、等待/已分配组成条、计划状态计数和累计事件条形。根据用户追加反馈，图形统一为深蓝、雾蓝、灰蓝，使用细环与细条，去除彩色分块和重复的小泊位图标；图例保持清楚的状态文字和数值。图形与数量来自同一真实 API，零值不画虚假进度，没有模拟增长率。

预约详情增加船舶场景和办理进度，显示船名、编号、状态及申请时间。进度代表 DRAFT → PENDING → APPROVED → COMPLETED 的预约生命周期；驳回与撤销显示终止，不冒充 AIS 航程，撤销不推断此前经过批准。场景图仍是有来源的装饰素材，不是记录对应的实船照片。

审核资料包含船舶/船型/船公司、IMO/MMSI、尺寸、最大吃水、吨位、到访计划和前后港、箱量/货重、申请时间、预计作业时长、申报吃水、优先级、危险品、特殊要求、提交时间及审核事实。列表仍用轻量字段，完整资料按所选主键独立获取。

## 4. 3B 演示路径与输入输出

1. 使用“审核员”登录，进入“进港预约”，点击“待审核”。
2. 选择一条预约，阅读右侧船舶及申报资料；展开“到访计划”可查看计划及前后港。
3. 点击“批准预约”，可以填写意见；或点击“驳回”，必须填写原因。确认框显示绑定的船名及预约编号。
4. 确认后，API 从真实会话获取审核人，将主键、决定和意见参数化交给事务过程。
5. 数据库复核审核角色、启用状态与 PENDING 状态，在同一事务中更新状态、审核人、数据库时间和前后审计快照。成功提交后 API 才确认成功。
6. 前端刷新清单、当前详情和总览。记录离开“待审核”筛选，右侧继续保留刚处理记录；总览待审核减少一条，批准或驳回增加一条。

| 输入 | 处理 | 输出 |
|---|---|---|
| 选审核员并登录 | 真实认证、设置 HttpOnly Cookie，返回身份/权限/CSRF | 左下显示林悦、审核员 |
| GET /api/appointments/{id} | 按预约主键关联完整申报与历史基础资料 | 完整详情；不存在返回 404 |
| POST /api/appointments/{id}/review，decision=APPROVED，reviewComment=意见 | 会话审核人 + 事务过程 | 200，主键字符串和 APPROVED；详情独立重读 |
| decision=REJECTED，原因非空 | 同一事务路径，原因去空白 | 200，REJECTED；保留审核历史 |
| 空白驳回、非法决定、超长意见、伪造审核人字段 | API 输入边界拒绝 | 400，无业务或审计残留 |
| 未登录或无审核权限 | API 授权；过程也复核角色 | 401/403 |
| 重复审核或两人同时审核 | 同港事务锁及状态复核 | 重复 409，并发最多一个成功 |

写入后数据库中的预约和审计会真实改变，不是仅在浏览器改颜色。已驳回记录保留原事实，重新申请应在后续登记功能创建新记录；不把它改回草稿掩盖审核历史。

提交失败保留意见；会话令牌失效可恢复后再次明确确认。若提交响应丢失，界面提供“查看最新状态”，先读取实际结果，不自动重放写操作。若已经确认写成功而清单刷新失败，会同时说明审核成功和清单待刷新，不提示再次审核。

## 5. 前端、后端与数据库分别做了什么

| 层次 | 本轮新增或修改 |
|---|---|
| 前端 | 四账号选择、准确登录错误；图文总览与字号；完整详情和办理进度；批准/驳回确认、提交保护、三处刷新和异常恢复 |
| 后端 | 开发账号初始化与可用选项查询；登录模型错误分类；完整详情契约；审核 POST、权限和 CSRF、防操作者伪造、业务错误映射 |
| 数据库 | 在原审核过程加入 ADMIN/REVIEWER 锁内授权和空白原因校验；补齐详情 SELECT 及必要列读取权限；不增加业务表/视图/过程 |
| 数据 | 本机增加四个专用登录账号及其脱敏维护审计；已有 53 条预约与 42 条事件未因自动验收被改写 |

本机已部署 `04_procedures.sql`、`09_permissions.sql`。仍为 21 张基本表、3 个业务视图、7 个过程、8 个表级触发器；不需要重新运行 `01_schema.sql`。详情 SQL 随后端程序集嵌入更新。已有账号与预约基础没有重置。

关键新增文件：`DemoAccounts.cs` 管理专用账号；`AppointmentDetail.cs` 定义完整资料；`IAppointmentReviews.cs` 定义写契约；`SqlAppointmentReviews.cs` 执行既有事务；`AppointmentReviewController.cs` 负责 HTTP 边界；`AppointmentProgress.vue` 表达办理状态；`AppointmentReview.vue` 管理确认及恢复。全项目职责见 [文件索引](../file-guide.md)。

## 6. 启动、验收和边界

日常仍用两个长期终端：一个运行 ASP.NET Core 5180，一个运行 Vite 5173。无需为本轮重装依赖或重建数据库。完整命令见 [启停手册](../runbook.md)。若已运行，直接刷新现有前端；避免重复占用端口。

本轮 Release 构建、73 项后端测试、59 项独立数据库回归、19 个 SQL 文件静态解析通过；前端类型检查与生产构建通过。浏览器完整验收和独立审查的最终证据见 [3B review](../reviews/2026-11-09-stage3b-review.md)。登录/审核测试使用随机独立 SQL 库与真实 API，结束清理，不写开发库业务。

本轮未接入登记、草稿编辑、提交、撤销、锚地/泊位写页面、实时 AIS 和移动设备传感器。浏览器验证使用 Windows Edge，真实手机软键盘、Safari/Firefox、读屏器和公网部署未验收。当前开发 API 沿用本机 Windows 数据库身份，最小权限角色经独立用例验证；不能将其说成生产部署已完成。

下一批 3C 开工前细化“登记 → 保存草稿 → 编辑 → 提交 → 3B 审核”的事务及表单验收；重点处理编号去重、提交时效、船舶/船型启停、吃水/作业时间和失败无残留。中期演示可先使用现有待审核场景完整展示 3B，保留阶段边界。
