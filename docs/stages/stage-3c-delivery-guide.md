# PortQueue 阶段 3C 交付与操作说明

本轮承接 3B，新增预约登记、草稿编辑和提交审核。现在可以从页面完成“调度员登记 → 保存草稿 → 修改 → 提交 → 审核员批准或驳回”。总览按本轮参考调整，四个业务入口均接到真实查询页。

## 本轮与上一轮的区别

| 范围 | 上一阶段 3B | 本轮 3C |
| --- | --- | --- |
| 身份与审核 | 四个真实账号、角色、登录、批准/驳回 | 复用身份；登记权限由 ADMIN / DISPATCHER 承担 |
| 预约页面 | 查询已有预约、完整申报、审核 | 增加登记抽屉、编辑草稿、提交确认、写入后的刷新 |
| 总览 | 预约状态环图、旧作业概要、主图标题 | 明亮蓝色、真实港口资料、作业类别切换图、四个实际入口与宽松页脚 |
| 其他业务 | 仅概要与最近事件 | 锚地排队、泊位计划、进出港记录的分页查询，可回到关联预约 |
| 数据库 | 21 表、3 视图、7 过程、8 触发器 | 21 表、3 视图、8 过程、8 触发器；新增登记事务，无新基本关系 |

## 当前可直接操作的路径

前端地址 `http://127.0.0.1:5173/`，API 地址 `http://localhost:5180/`。在 VS Code 仓库根目录打开两个终端：

```powershell
# 终端一：后端
dotnet run --project src/PortQueue.Api --configuration Release
```

```powershell
# 终端二：前端
pnpm --dir web/port-queue-web run dev
```

本机增量数据库已部署，无须重跑建表文件。新环境或其他旧环境按 `database/README.md` 的依赖顺序部署 `14 → 09`；12 是名称整理脚本。SQL 查询文件嵌入后端，修改查询文件后需要构建并重启 API。

1. 登录窗口选择“调度员”或“管理员”，初始密码 `123456` 自动填入。这是 Development 下的真实专用账号，不是前端角色模拟。
2. 打开“进港预约”，点击“登记预约”。按船名、IMO 或 MMSI 搜索，并从实际候选中选择船舶；候选支持翻页和键盘上下键、Enter、Escape。
3. 填写申请到港、申请离港、预计作业时长、申报吃水和航次计划时间。上一港、下一港、箱量、货重、计划离港及特殊要求允许留空。
4. 航次计划和申请时间是两个业务事实。“沿用申请时间”只在主动点击时复制，不会在后续编辑中悄悄覆盖。
5. 点“保存草稿”，列表及详情读取刚保存的记录；选中草稿后可以“编辑草稿”。修改后再保存，版本冲突时先读取最新内容。
6. 点“提交审核”并确认；也可以在新登记时直接提交。提交后变为“待审核”，不再开放草稿编辑。
7. 切换“审核员”处理批准或驳回；管理员也可直接审核。审核权限、过程和留痕复用 3B。

所有页面时间按北京时间显示。历史草稿的申请到港可能已经过去，必须先修改为将来时间，才能提交；不能为了演示而放开这一校验。

## 一条具体输入输出

选中已登记船舶，输入申请到港 `2032-04-12 08:00`、申请离港 `2032-04-13 20:00`、作业 `8.5` 小时、吃水 `8` 米、箱量 `230 TEU`。填写航次计划后保存。

浏览器发送业务字段和本次登记请求标识 → API 验证会话、CSRF、字段、时区和小数精度 → 登记过程重新检查角色、引用和值域 → 同一事务创建 PLANNED 航次、DRAFT 预约及两份审计快照 → 返回预约主键和版本 → 页面独立刷新列表、详情、总览。

将箱量改为 `260 TEU` 后保存，再提交审核，数据库修改为 PENDING 并记录提交时间；审核员批准后为 APPROVED，责任人和审核时间来自服务器。上述场景已在隔离测试库运行，不会把验收预约混进开发库。

## 新增接口

| 接口 | 输入 | 输出与边界 |
| --- | --- | --- |
| `GET /api/ships`、`GET /api/ports` | keyword、page | 启用资料候选、总数、20 条分页；船舶还核验启用 SHIP_TYPE |
| `POST /api/appointments` | requestKey、data、submit | 新建 201；原键原内容重放 200；冲突 409 |
| `PUT /api/appointments/{id}/draft` | expectedVersion、data | 仅修改草稿；旧版本或已提交返回 409 |
| `POST /api/appointments/{id}/submit` | expectedVersion | 只提交当前草稿，不接受覆盖申报资料或伪造操作者 |
| `GET /api/business/queue` | keyword、page | 锚地、队列位置、状态及实际进出锚时间 |
| `GET /api/business/plans` | keyword、page | 泊位、当前版本、状态和计划靠离泊时间 |
| `GET /api/business/events` | keyword、page | 真实事件、发生时间、记录人和关联预约 |

未登录写入返回 401，无权限 403，输入错误 400，不存在 404，状态/版本冲突 409。成功响应与后续查询分开；刷新失败不把成功保存误报为失败。

## 数据与可靠性

- 创建请求使用 UUID 映射唯一预约编号，创建审计保存请求指纹及操作者。重复点击或丢失响应后核对原请求不会创建第二份事实；相同键改内容或换操作者会被拒绝。
- 数值尾零不改变业务含义：重试中的吃水 `8` 与 `8.00` 会按同一数值处理。业务查询失败后，“重新读取”保留失败请求的关键词和页码，不悄悄切回旧查询。
- 草稿版本取该预约及航次的最新审计序号，不增设冗余版本列。并发编辑或提交只有一个版本获准继续。
- 业务与审计同事务；数据库重验角色、船型、启用状态、时间、吃水、作业时长及数量。触发器和最小权限继续兜底。
- 开发库仍是 53 条预约、42 条事件。5 个初始显示名称整理为中文，保留原标识并追加审计；设施数量为本系统已登记的 3 座码头、4 处锚地、3 个泊位，不代表现实青岛港的总规模。
- 港口选择器仅返回已启用的基础资料；当前参考库只有一个港口，因此港口候选较少。上一港、下一港允许留空，不应为了填满选择器而伪造已维护资料。
- 三个新查询页面使用已有视图，展示所有符合条件的记录，支持分页；没有 AIS、地图或传感器数据冒充实时信息。
