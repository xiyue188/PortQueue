# 阶段 1 数据库业务基线 review

## 范围

本阶段只完成数据库业务对象、事务边界、验收用例和可重复演示数据，不接入真实 API，不改前端原型，不修改 21 个基本关系的语义。

## 交付结果

- `usp_adjust_queue`：锁定同一锚地有效队列，保存全部受影响记录的前后序号和人工原因；离锚与自动补位不伪造人工调整记录。
- `usp_create_berth_plan_revision`：首次创建计划同时生成当前版本；草稿修订切换当前版本；已确认或执行中修订先保留候选版本。
- 现有 5 个过程统一加入操作人状态、事务回滚、应用锁、未来事件和状态流转检查，并补充审计快照。
- 事件时间线使用实际事件前最后确认的版本作为执行基准；执行中确认新版本保持 `EXECUTING`，离泊仍沿用靠泊基准。
- 新增字典标识保护和审计追加保护两个表级 DML 触发器。`Programmability > Database Triggers` 仍为空是数据库级 DDL 触发器分类问题。
- `09_permissions.sql` 创建 `portqueue_app` 角色和 `portqueue_probe` 无登录验证用户；允许视图查询和业务过程执行，拒绝直接业务表写入、密码列读取、孤立事件和伪造审计。
- `10_seed_demo.sql` 提供 PQ-DEMO 业务事实，重复执行不覆盖业务进度；`11_statistics.sql` 固定等待、偏差、准点率和泊位观测利用率口径。
- `06_smoke_tests.sql` 将对象数量、约束可信状态和禁用触发器变成失败即停的验收条件。

- 50 个业务、负向、事务回滚、审计和权限用例；
- 4 个两个独立 SQL 连接的并发用例；
- 5 个集成用例：旧 06/07/08 回归、对象与约束状态、演示幂等与指标、保留已推进预约状态、停用字典状态保留；

## Review 中发现并修复的问题

1. 原离锚过程留下队列序号空位、离锚未核对锚地、取消但仍在场被遗漏：按实际未离开事件查找停留，离开后重排，并计入容量。
2. 原确认过程可能把 EXECUTING 改回 CONFIRMED：确认保留执行状态，禁止执行中改泊位与计划靠泊时间。
3. 原始计划创建没有受控入口、草稿当前版本语义与定稿不一致：原子创建计划和版本 1，候选与当前分开处理。
4. 过程异常没有统一清理事务：全部入口 TRY/CATCH，错误回滚整个工作单元；用故意令审计 INSERT 失败的用例验证原子性。
5. 原参考种子会重新启用已停用字典，演示账户写死密码散列：种子仅补缺，新的演示操作人使用随机无登录占位值。
6. 原索引查询把系统索引算入 203：明确筛选 dbo 用户表，结果为 45；没有删除业务索引。
7. 并发测试最初以 sqlcmd 输出作为屏障，受到缓冲影响：改为检查引擎应用锁授予状态后再启动第二个连接，验证实际阻塞和冲突结果。
8. bootstrap 新库流程和已有库流程分别审查：新库包含 05 和 09；已有库不在启动时更新业务过程，升级采用明确的 SQL 部署步骤。
9. 演示脚本在普通 sqlcmd 连接首次执行时因 QUOTED_IDENTIFIER 默认值失败，事务已整体回滚：脚本显式声明过滤索引要求的 SET 选项；验收部署改用不带 `-I` 的连接，避免测试环境掩盖客户端差异。

## 风险与边界

- 最小权限已在数据库角色层验证；当前 LocalDB 连接所有者仍为 Windows 管理员，不能宣称 ASP.NET 已经使用低权限连接账号。后续部署到独立 SQL Server 实例时再由管理员创建实际 Windows 登录映射。
- 操作人参数仍由调用者提供，只验证启用状态；可信身份绑定和业务角色授权需在后续 API 阶段实现。现有 21 表定义未变，直接管理员 DML 可以绕过部分业务流程，业务应用必须通过授权过程写入。
- 应用锁适合单港课程设计和当前并发规模，保证调序、版本切换和事件写入不会相互覆盖；尚未做吞吐量优化。
- `10_seed_demo.sql` 是合成答辩数据，不是 AIS 轨迹或真实港口数据；不会由 bootstrap 自动加载。
- 当前前端仍为 Mock 原型。阶段 1 完成后，下一阶段才是预约查询真实 API 联调。
- 当前阶段只补齐所列七个数据库操作；预约登记、撤销及基础资料维护写入口随各自功能阶段实现，不将本次基线完成等同于全部业务功能完成。

## 阶段门结论

数据库业务基线达到阶段 1 验收条件，可以进入阶段 2：数据库只读 API 联调。进入下一阶段前不再扩大数据库对象范围。
