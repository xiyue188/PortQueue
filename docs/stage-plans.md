# PortQueue 分阶段实施计划与验收标准

本文档把实施路线拆成可以独立开发、独立演示和独立 review 的小阶段。每阶段开始前先确认范围，完成后必须保存构建、测试、数据库验证和界面截图等证据。未达到本阶段验收标准时，不进入下一阶段。

## 阶段 0：仓库与运行基线（已完成）

### 目标

建立 VS Code、SQL Server、ASP.NET Core、Vue 3 和 Git 的可重复运行基线。

### 已交付

- 21 张表、3 个业务视图、核心触发器和第一版事务过程。
- ASP.NET Core 健康接口和 SQL Server 连接工厂。
- Vue 调度总览原型，明确标注演示数据。
- 中文小步提交、GitHub 首次推送、目录职责索引和启动手册。

### 验收标准

- `dotnet build` 无警告、无错误。
- API 健康接口返回 HTTP 200。
- 前端 `pnpm run build` 通过。
- SQL 结构检查返回 21 张表、3 个视图。
- 业务和约束冒烟测试通过且测试数据回滚。

## 阶段 1：数据库业务对象补齐（下一数据库阶段）

### 目标

完成数据库基线中尚未实现、但已经在物理设计和教师要求中明确的对象，为后端真实联调提供稳定的事务入口。

### 本阶段范围

1. 队列人工调序存储过程：锁定同一锚地的有效队列，校验新序号，保存前后序号和调整原因。
2. 泊位计划版本创建存储过程：校验计划状态，按计划内版本号递增，创建草稿版本，不改变当前版本。
3. 通用审计触发器或受控审计写入：记录关键操作的对象、操作类型、操作者和 JSON 快照，只追加不覆盖。
4. 数据库专用登录/用户与最小权限脚本：应用账号只能执行规定过程和查询视图，不能直接修改业务表。
5. 可重复的完整演示数据：准备一条预约、锚地队列、泊位计划和执行时间线，重复恢复不会产生重复业务数据。
6. 统计查询和报表视图的设计确认：先明确指标口径和 SQL，再决定是否新增视图；不为了增加菜单而新增关系。

### 不在本阶段

- 不开发新的前端页面。
- 不开发完整 API。
- 不实现 AIS、地图、硬件传感器、复杂优化算法。
- 不修改 21 个基本关系的语义。

### 验收标准

- 调序过程在正常、序号越界、重复序号和并发场景下有明确结果。
- 新建计划版本不会改变当前版本；确认版本后仍保持每个计划最多一个当前版本。
- 关键操作产生审计快照，快照内容可以按对象和时间查询。
- 应用数据库用户无法直接执行业务表写入，但可执行授权过程和查询视图。
- 演示数据脚本可重复执行，业务编号和基础数据不重复。
- 现有 07、08 冒烟测试及新增负向测试全部通过。

### 阶段门

SQL 先完成 review，再进入 API。提交应拆为“过程与审计”“权限与演示数据”“测试与文档”三个中文小提交。

## 阶段 2：预约查询真实闭环

### 目标

把第一个真实业务读链路打通：SQL Server → Dapper → ASP.NET Core API → Vue 预约列表。

### 本阶段范围

- 预约列表查询 SQL 或基于现有视图的参数化查询。
- 预约查询 DTO、分页和状态筛选。
- API `GET /api/appointments`。
- 前端预约列表页，显示预约编号、船舶、计划到港时间、状态和审核信息。
- 加载中、空结果、接口失败三种页面状态。

### 验收标准

- 刷新页面后数据仍来自 SQL Server，浏览器开发者工具能看到 API 请求。
- 查询只使用参数化 SQL，不能拼接筛选值或排序字段。
- 分页边界、状态筛选和无数据结果有自动化测试。
- 数据库不可用时 API 返回稳定错误码，不能泄露 SQL Server 原文。
- 前端不再使用预约列表 Mock 数据；总览中的非本阶段指标仍可保留演示标记。

### 阶段门

至少保存一张真实预约列表截图、一条成功 API 测试、一条数据库故障测试和一次 review 记录。

## 阶段 3：预约登记与审核

### 目标

完成预约写入和审核操作，形成第一个可修改业务状态的前后端闭环。

### 本阶段范围

- 预约登记 API 和页面表单。
- 审核通过/驳回 API，调用 `usp_review_appointment`。
- 状态按钮按数据库状态控制可用性。
- 审核意见、审核人和审核时间展示。

### 验收标准

- 合法预约可以保存并查询。
- 未审核预约不能执行后续锚地或泊位操作。
- 重复审核、无效状态和不存在的预约被拒绝。
- 过程异常时整体回滚，不留下半条记录。
- 页面刷新后状态与数据库一致。

## 阶段 4：锚地队列

### 目标

实现预约通过后的锚地进入、队列查询、调序和离开。

### 验收标准

- 同一锚地有效队列序号唯一且连续。
- 重复进入、重复离开和时间倒置被拒绝。
- 调序原因、调整前后序号和操作者可追溯。
- 取消但尚未离锚的记录按规则计入在场统计。
- 至少完成两浏览器并发调序或进入测试。

## 阶段 5：泊位计划与时间窗

### 目标

实现候选泊位、计划版本、冲突检查和当前计划查询。

### 验收标准

- 船型、船长、吃水和载重吨的适配规则生效。
- 重叠时间窗被拒绝，首尾相接允许。
- 计划版本创建、确认和切换保持历史记录。
- 并发确认同一泊位时最多一个事务成功。
- 计划当前版本视图与页面显示一致。

## 阶段 6：实际执行与时间线

### 目标

实现实际进港、靠泊、离泊和单次到访的完整事件时间线。

### 验收标准

- 进港、靠泊、离泊事件各有正确分类关联。
- 重复事件、时间倒置和执行基准版本不一致被拒绝。
- 离泊后的预约、计划和到访状态正确结束。
- 时间线来自事件事实，等待时长和计划偏差在查询时计算，不重复存储。

## 阶段 7：统计、报表和答辩交付

### 目标

补充能体现数据库设计价值的统计和交付材料，完成可复现演示。

### 本阶段范围

- 平均等待时长、泊位使用率、计划偏差、准点率等统计查询。
- ECharts 图表和 CSV/Excel 友好导出。
- 典型正常场景和典型错误场景演示数据。
- 数据库恢复、API、前端和答辩说明统一校对。

### 验收标准

- 每项指标都有明确计算口径和来源字段。
- 报表结果可以由 SQL 查询复核，页面不自行编造指标。
- 干净环境可按文档恢复数据库并启动系统。
- 报告、代码、数据库对象和演示截图名称一致。

## 固定的阶段工作顺序

每个阶段都按以下顺序执行：

1. 写本阶段设计、文件清单和验收标准。
2. 只实现本阶段范围内的数据库对象、API、页面和测试。
3. 本地构建、单元/集成测试、SQL 冒烟测试和人工演示。
4. 深度 review，记录问题、修复和遗留风险。
5. 使用一个或多个中文小提交提交，并推送到 GitHub。
6. 阶段验收通过后，才开始下一阶段。
