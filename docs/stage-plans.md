# PortQueue 分阶段实施计划与验收标准

本文档把实施路线拆成可以独立开发、独立演示和独立 review 的小阶段。每阶段开始前先确认范围，完成后必须保存构建、测试、数据库验证和界面截图等证据。未达到本阶段验收标准时，不进入下一阶段。

### 阶段 1 工作顺序（归档）

1. **先核对现状**：以 `06_smoke_tests.sql`、`07_business_smoke_test.sql` 和 `08_constraint_smoke_tests.sql` 为基线，确认 21 张表、3 个视图、7 个业务过程和 8 个表级触发器仍然成立。
2. **补齐业务对象**：新增队列调序过程、泊位计划草稿版本过程和关键操作审计写入；每个对象先写输入、前置条件、事务动作、成功结果和失败结果。
3. **补齐运行边界**：增加应用数据库用户的最小权限脚本，并确认恢复脚本不会把密码、数据库文件或本机账号提交到 Git。
4. **准备可重复演示数据**：单独建立演示数据脚本，使用业务候选键保证重复执行不产生重复记录；测试脚本继续使用事务回滚，不与演示数据混用。
5. **补充负向测试**：覆盖调序越界、计划版本错误切换、审计快照缺失、越权写表和重复加载演示数据等场景。
6. **完成阶段 review**：执行 .NET 构建、自动化测试、SQL 静态检查和数据库恢复验证，结果写入 `docs/reviews/`，再拆成中文小提交。

### 阶段 1 范围边界（归档）

- 不开发预约列表 API 和前端真实查询；它们属于阶段 2。
- 不把当前 `App.vue` 的演示数据误称为真实业务数据。
- 不为了界面菜单新增表、视图或组件。
- 不新增没有业务含义的数据库级 DDL 触发器；现有 8 个触发器是表级 DML 触发器，按所属表检查。
- 不实现 AIS、地图、传感器和复杂排队优化算法。

### 阶段 1 的完成证据

- SQL 对象清单：21 张表、3 个视图、7 个业务过程、8 个表级触发器和业务表索引数量。
- 正常业务链路结果：预约审核、锚地事件、泊位计划、实际进港、靠泊和离泊。
- 负向测试结果：非法状态、错误字典类型、时间冲突、调序错误和越权写入均被拒绝。
- 演示数据重复执行前后行数一致，测试数据回滚后数据库没有残留。
- `dotnet build`、`dotnet test`、前端类型检查和构建结果。
- 一份 review 记录；按可运行或可审查的功能边界做中文小提交，不以固定提交次数合并不相关工作。

## 阶段 0：仓库与运行基线（已完成）

### 目标

建立 VS Code、SQL Server、ASP.NET Core、Vue 3 和 Git 的可重复运行基线。

### 已交付

- 21 张表、3 个业务视图、核心触发器和第一版事务过程。
- ASP.NET Core 健康接口和 SQL Server 连接工厂。
- Vue 调度总览原型，明确标注演示数据。
- 中文小步提交、GitHub 首次推送、目录职责索引和启动手册。

### 验收标准

- `dotnet build` 无警告、无错误。
- API 健康接口返回 HTTP 200。
- 前端 `pnpm run build` 通过。
- SQL 结构检查返回 21 张表、3 个视图。
- 业务和约束冒烟测试通过且测试数据回滚。

## 阶段 1：数据库业务对象补齐（本轮完成）

### 目标

完成数据库基线中尚未实现、但已经在物理设计和教师要求中明确的对象，为后端真实联调提供稳定的事务入口。具体用例和验证结果以阶段 1 review 为准。

### 本阶段范围

1. 队列人工调序存储过程：锁定同一锚地的有效队列，校验新序号，保存全部受影响记录的前后序号和调整原因。
2. 泊位计划版本创建存储过程：首次创建同时生成当前版本，草稿修订切换当前版本，确认/执行中修订先保存候选版本。
3. 受控审计写入与追加保护：记录关键操作的对象、操作类型、操作者和 JSON 快照，只追加不覆盖。
4. 数据库最小权限角色与无登录验证用户：仅授予规定过程、视图和预约查询列，不能直接修改业务表。实际 Windows 登录映射在 API 部署时接入。
5. 可重复的完整演示数据：准备一条预约、锚地队列、泊位计划和执行时间线，重复恢复不会产生重复业务数据。
6. 统计查询和报表视图的设计确认：先明确指标口径和 SQL，再决定是否新增视图；不为了增加菜单而新增关系。

### 不在本阶段

- 不开发新的前端页面；阶段 2 才开始预约查询真实 API。
- 不开发完整 API。
- 不实现 AIS、地图、硬件传感器、复杂优化算法。
- 不修改 21 个基本关系的语义。

### 验收标准

- 调序过程在正常、序号越界、重复序号和并发场景下有明确结果。
- 首次建计划和草稿修订保证恰好一个当前版本；已确认/执行中候选不提前改变当前安排；确认失败保留原版本。
- 关键操作产生审计快照，快照内容可以按对象和时间查询。
- 应用数据库用户无法直接执行业务表写入，但可执行授权过程和查询视图。
- 演示数据脚本可重复执行，业务编号和基础数据不重复。
- 现有 07、08 冒烟测试及新增负向测试全部通过。

### 阶段门

SQL 和对应验收先完成 review，再进入 API。先提交设计，再提交可验证的数据库实现与测试，最后提交部署说明与 review；每个提交包含可审查的完整变更。

## 阶段 2：预约查询真实闭环（实现与浏览器交互验收完成）

### 目标

把第一个真实业务读链路打通：SQL Server → Dapper → ASP.NET Core API → Vue 预约列表。

### 本阶段范围

- 预约列表查询 SQL 或基于现有视图的参数化查询。
- 预约查询 DTO、分页、状态筛选和字面关键词查询。
- API `GET /api/appointments`。
- 独立 `GET /api/overview`：跨业务指标与近期事件，使用现有表和视图。
- 前端预约列表页，显示预约编号、船舶、申请到离港时间、状态和审核信息。
- 加载中、空结果、接口失败三种页面状态。

### 验收标准

- 刷新页面后数据仍来自 SQL Server，浏览器开发者工具能看到 API 请求。
- 查询只使用参数化 SQL，不能拼接筛选值或排序字段。
- 分页边界、状态筛选和无数据结果有自动化测试。
- 数据库不可用时 API 返回稳定错误码，不能泄露 SQL Server 原文。
- 预约与总览均读取数据库；未接入指标不伪造，API 失败不回退 Mock。

### 阶段门

已保存真实 API、代理查询、失败契约、构建、SQL 静态检查和 review 证据。2026-11-07 通过 Playwright 驱动本机 Edge 完成六项浏览器检查，补齐桌面、窄屏、空结果、错误恢复截图。中期演练仍须亲自复现讲解顺序，并准备数据库结构和规则对照材料。

2026-11-08 先扩展至七项浏览器用例，随后交互改进扩展至 13 项。2026-11-09 完整搜索、动态轮播与独立详情选择扩展至 22 项浏览器用例，最新全量全部通过，同时通过后端 46 项测试及 17 份 SQL 静态检查。当前范围及条件见 `stages/stage-2-search-and-events.md`，最终结果见 `reviews/2026-11-09-search-and-events-review.md`；旧验收记录保留为历史证据。

## 阶段 3：预约登记与审核（3A 已完成验收）

完整设计见 [阶段 3 设计与验收矩阵](stages/stage-3-appointment-workflow.md)。2026-11-08 仅规划；用户在 2026-11-09 授权启动后，先实现 3A 身份权限，总览职责收口同批完成。预约审核与登记尚未实现，不把只读界面优化计为写业务完成。

### 目标

完成预约写入和审核操作，形成第一个可修改业务状态的前后端闭环。

### 本阶段范围

分三批展开，每批开始时再写文件清单与详细用例：

- **3A 身份与权限**：沿用四类角色和单角色账号模型；Cookie 会话、标准密码哈希、停用/退出失效、401/403、写请求防伪造。后端从会话确定操作者，不接受客户端冒充。菜单按真实权限显示。
- **3B 预约审核**：完整申报详情查询；批准/驳回 API 调用 `usp_review_appointment`；角色授权、重复操作和失败回滚；审核后列表、详情、总览同步更新。
- **3C 预约登记与提交**：完善受控写入事务和页面表单，覆盖保存/编辑草稿、提交、重试去重和非法字段；撤销另列关联队列/计划的一致性用例。

### 验收标准

- 合法预约可以保存并查询。
- 未审核预约不能执行后续锚地或泊位操作。
- 重复审核、无效状态和不存在的预约被拒绝。
- 过程异常时整体回滚，不留下半条记录。
- 页面刷新后状态与数据库一致。
- 未登录、角色越权、伪造操作者和停用账号均不能成功写入；失败无业务残留。

本轮 3A 的实现范围与逐项验收见 [身份权限与总览职责收口](stages/stage-3a-session-and-overview.md)。3B 审核、3C 登记提交仍分别开工，禁止把本批身份功能计为预约写入完成。

## 阶段 4：锚地队列

### 目标

实现预约通过后的锚地进入、队列查询、调序和离开。

### 验收标准

- 同一锚地有效队列序号唯一且连续。
- 重复进入、重复离开和时间倒置被拒绝。
- 调序原因、调整前后序号和操作者可追溯。
- 取消但尚未离锚的记录按规则计入在场统计。
- 至少完成两浏览器并发调序或进入测试。

## 阶段 5：泊位计划与时间窗

### 目标

实现候选泊位、计划版本、冲突检查和当前计划查询。

### 验收标准

- 船型、船长、吃水和载重吨的适配规则生效。
- 重叠时间窗被拒绝，首尾相接允许。
- 计划版本创建、确认和切换保持历史记录。
- 并发确认同一泊位时最多一个事务成功。
- 计划当前版本视图与页面显示一致。

## 阶段 6：实际执行与时间线

### 目标

实现实际进港、靠泊、离泊和单次到访的完整事件时间线。

### 验收标准

- 进港、靠泊、离泊事件各有正确分类关联。
- 重复事件、时间倒置和执行基准版本不一致被拒绝。
- 离泊后的预约、计划和到访状态正确结束。
- 时间线来自事件事实，等待时长和计划偏差在查询时计算，不重复存储。

## 阶段 7：统计、报表和答辩交付

### 目标

补充能体现数据库设计价值的统计和交付材料，完成可复现演示。

### 本阶段范围

- 平均等待时长、泊位使用率、计划偏差、准点率等统计查询。
- ECharts 图表和 CSV/Excel 友好导出。
- 典型正常场景和典型错误场景演示数据。
- 数据库恢复、API、前端和答辩说明统一校对。

### 验收标准

- 每项指标都有明确计算口径和来源字段。
- 报表结果可以由 SQL 查询复核，页面不自行编造指标。
- 干净环境可按文档恢复数据库并启动系统。
- 报告、代码、数据库对象和演示截图名称一致。

## 固定的阶段工作顺序

每个阶段都按以下顺序执行：

1. 写本阶段设计、文件清单和验收标准。
2. 只实现本阶段范围内的数据库对象、API、页面和测试。
3. 本地构建、单元/集成测试、SQL 冒烟测试和人工演示。
4. 深度 review，记录问题、修复和遗留风险。
5. 使用一个或多个中文小提交提交，并推送到 GitHub。
6. 阶段验收通过后，才开始下一阶段。
