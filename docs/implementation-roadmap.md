# PortQueue 实施路线

## 1. 实施目标

本项目将前四阶段的设计落实为一个能够在本机恢复、运行和演示的数据库应用系统。系统只服务一个港口，围绕一次本港到访形成预约、锚地排队、泊位计划和实际事件的闭环。开发重点放在数据库对象、事务边界、历史追溯和复杂查询上，不扩展为港口综合管理平台。

最终版本必须能够完成两条业务路径：

1. **锚地路径**：新建到访和预约，审核通过，登记进入锚地，查看队列，确认泊位计划，登记进港、靠泊和离泊。
2. **直接靠泊路径**：新建到访和预约，审核通过，直接确认泊位计划，登记进港、靠泊和离泊，不创建虚假的锚地停留记录。

两条路径使用相同的船舶、泊位、计划版本和事件模型，统计结果按实际事件生成。

## 2. 阶段与门槛

| 阶段 | 交付物 | 完成门槛 |
|---|---|---|
| A 物理设计与业务操作 | SQL Server 类型映射、21 表、索引、3 视图、核心过程、操作契约 | 每个业务操作均有输入、前置条件、事务边界、成功结果和失败结果 |
| B 数据库落地 | 可重复执行的建库脚本、种子数据、约束测试 | 脚本可从空数据库恢复；错误引用、错误状态、时间冲突被拒绝 |
| C 后端骨架 | API、配置、异常模型、数据库连接、过程调用适配 | `/health` 可用，API 不把 SQL 异常直接暴露给用户 |
| D 首条闭环 | 预约审核、计划确认、靠泊和离泊接口与页面 | 所有写入来自真实数据库，刷新页面后状态仍一致 |
| E 五区域功能 | 基础资料、预约、队列、泊位、执行统计 | 功能说明中的输入、输出和约束均有页面入口或查询结果 |
| F 质量和展示 | 统计报表、异常场景、性能检查、答辩演示 | 每个特色场景有可复现数据和截图，数据库备份可恢复 |

## 3. 当前阶段 A 的决策

### 3.1 物理类型

- 标识统一使用 `bigint identity(1,1)`；生成方式不改变关系模型中的业务含义。
- 代码使用 `varchar`，中文业务文本使用 `nvarchar`。
- 时间使用 `datetime2(0)`，系统内部保存 UTC，业务展示按本港时区转换。
- 金额不属于当前业务范围；长度、吃水和吨位使用定点 `decimal`，避免浮点误差。
- 审计快照使用合法 JSON 文本，不能把快照当作业务关系重新维护。

### 3.2 键与引用

字典项以 `dictionary_item_id` 为主键，`(dictionary_type, item_code)` 为候选键。船舶和泊位适用船型都真实引用字典项主键，触发器再检查目标类型为 `SHIP_TYPE`。所有外键使用 `NO ACTION`，历史记录阻止被引用资料物理删除。

### 3.3 约束分工

| 约束类型 | 由谁负责 |
|---|---|
| 主键、候选键、字段非空和简单范围 | 表定义、`UNIQUE`、`CHECK` |
| 引用存在和历史删除保护 | 外键 |
| 船型字典项类型与新引用启用状态 | 触发器和业务过程 |
| 预约审核、队列事件、计划确认、版本切换 | 事务存储过程 |
| 一个计划最多一个当前版本 | 过滤唯一索引 |
| 一个计划至少一个当前版本 | 创建和切换版本的同一事务 |
| 一个事件仅有一个正确分类关联 | 分类触发器加受控事务过程 |
| 审计快照 | 受控写入过程；后续阶段增加通用审计触发器 |

## 4. 实施顺序

1. 在 SQL Server 上执行 `database/00_create_database.sql` 至 `04_procedures.sql`。
2. 使用最少量参考数据验证表、索引、视图和过程，修复脚本后再编写后端数据库适配。
3. 后端先实现过程调用和查询 DTO，再实现页面；页面不直接拼写业务 SQL。
4. 先贯通一个预约，再补齐列表、筛选、分页、统计和导出。
5. 所有新增功能补充操作契约和验收用例，经过一次 review 后再合并。
