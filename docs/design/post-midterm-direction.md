# 后续模块的设计取舍与复盘

更新：2026-11-27。状态：用户已选择方案 A；本文是设计依据，不代表功能已经实现。进度只看 [实施计划](../stage-plans.md)，验收只看 [验收计划](../acceptance-plan.md)。

## 1. 要解决的实际问题

目标是：老师能直观看懂系统，操作人员能连续办完业务，结果可在数据库中核对。用户已确认保留冰蓝商务风格、共用角色页面，以图表和时间轴帮助判断；锚地可拖动调序，泊位可拖动排期，修改经简洁确认后保存。

当前主要矛盾不是“表格太多”本身，而是把数据库能查询什么直接变成页面：缺少任务主次，用解释小字弥补组织不足，再用相似面板塞满空位。只删字会丢掉判断条件，只加图会增加信息噪声，只换布局会把相同业务状态复制多份。必须先确定每页的对象、判断和下一步，再选择呈现形式。

另一个根因是范围追踪失真：正常主线与大量既有测试容易掩盖正式报告中的未实现能力。基础维护、撤销、已批准条件变更重审、计划取消和实际时间更正均须在最终验收中有对应项。

## 2. 三版方案与选择

| 方案 | 组织方式 | 强项 | 最强反对意见与成本 |
|---|---|---|---|
| **A 业务任务型（已选）** | 保留模块导航；队列、排期、待办时间线、统计各有任务主视图 | 与原需求和数据库用例对应，便于逐批开发及答辩 | 跨模块切换可能割裂；必须提供带对象定位的下一步入口和数据失效机制 |
| B 到访旅程型 | 选一次到访，在一张业务档案内连续查看预约、锚泊、计划和执行 | 单条闭环清楚，历史追溯自然 | 可能忽略全港资源冲突，并重现“选中一船就只剩一船”；适合作为详情，不作为全局工作台 |
| C 资源调度型 | 锚地、泊位和时间窗占据主画面，任务围绕资源展开 | 调度态势直观，资源约束突出 | 审核与历史任务不自然，小屏和直接操作复杂；适合泊位模块，暂不扩展成全系统控制台 |

A 为主方案，在所选到访详情中借鉴 B 的时间线，在泊位页借鉴 C 的资源排期；用户已明确确认这一组合。若试用时同一任务仍需反复跨页寻找下一步，应先改衔接，不添加另一套“超级工作台”。拖动列入锚地和泊位的分批交付；地图、3D和四套角色前端不作为前提。

### 一次到访串起完整业务

主线是“船方提供资料 → 调度员登记提交 → 审核员批准 → 按需入锚候泊 → 安排并确认泊位 → 如在锚地则实际离锚 → 实际进港、靠泊、离泊 → 统计回查”。无需等泊时跳过锚地；驳回、撤销和变更重审保留分支，不能为了讲故事强制走直线。计划编制可以早于实际入锚，不把展示顺序变成多余的数据库限制。

| 衔接 | 用户看见和操作 | 数据与导航约定 |
|---|---|---|
| 总览 → 业务模块 | 点击待办/图形进入相应范围 | 状态筛选明确可见；不将总览变成单船首页 |
| 预约 → 锚地/泊位 | 在所选到访中继续“登记入锚”或“安排泊位” | 带入本次到访和预约身份；无权者只可查看，有权者按真实状态办理 |
| 队列 → 泊位 | 选船后安排时间窗，仍能查看其他船和资源 | 携带选中对象，不将整个资源图过滤为该船；返回保留锚地、筛选、滚动位置 |
| 泊位 → 实际记录 | 从计划打开该次到访，看到下一项可登记动作 | 已确认安排与已发生事实分开；不能拖动计划条生成进港或靠泊事件 |
| 时间线/统计 → 原记录 | 点时间节点或图表样本回查申请、计划版本或实际记录 | 使用真实主键定位；返回恢复原查询，不凭船名匹配到另一趟到访 |

关联主键沿用 `port_call_id` 和其唯一对应的 `appointment_id`，不增加一套“旅程表”。共享的是对象身份和事实查询契约；各页保存自己的筛选、滚动及选择。详情按需展开时间线，避免每页永久重复整条流程。未发生节点显示待办理或适用计划时间，不能补造实际时间；业务发生时间与审计操作时间分别展示，补录不按录入时间冒充发生顺序。

报告和演示沿同一组到访、预约、计划、事件及审计标识取证：一份申请如何成为安排、如何实际执行、如何进入统计。图表不单独准备无法回查的展示数字。

### 拖动与轻巧反馈

| 场景 | 操作设计 | 保存与约束 |
|---|---|---|
| 锚地调序 | 在同一锚地的完整有效队列中抓住拖动柄，其他行平滑让位；显示目标顺位，松手后只要求确认变化和填写原因 | 如从第5位移至第2位，预览受影响的第2—4位顺移；确认后事务更新并记录全部调整。拖回原位无写入。搜索/分页隐藏其他成员时不直接调序，提供“打开完整队列调序”入口，不拿屏幕行号当真实顺位 |
| 泊位排期 | 在真实时间比例的资源图中拖动待安排对象或计划条；横向改时间、纵向换候选泊位，显示旧位置轮廓与新安排；默认15分钟吸附，确认表单可精确到分钟 | 草稿保存与正式确认分开；已确认计划产生候选版本，确认后才替换当前安排；执行中仅允许规则许可的计划离泊调整，不移动已经发生的靠泊事实。超出范围、不适配、冲突均有文字反馈 |
| 时间线与图表 | 点节点查详情、点图形查样本；返回恢复上下文 | 图表选择明确显示筛选条件，可清除；不把选择和状态写入混在一起 |

15分钟只是拖动输入的默认网格，不是数据库时间精度或港口作业规则；已有非整刻度计划不会在打开或点击时被自动取整。单次拖动只提出一个变更，不自动连带重排其他计划；草稿可展示冲突预警，确认占用仍由事务裁决。首批不做时间条边缘缩放、跨锚地拖船或批量自动排程，时长通过同一确认表单修改。

所有拖动采用“预览 → 确认 → 服务端及数据库验证 → 读回”的同一语义。确认区只列对象、前后差异、必要原因及冲突反馈；不加一页操作说明。Escape/取消恢复未保存预览；保存后若要恢复旧安排，重新走受控调整并留审计。无权用户没有拖动柄；触摸、键盘和“移至第几位/编辑安排”入口具备等价能力。拖动期间的刷新不能改变抓取对象，确认前必须检查队列/版本是否已变化；冲突时显示最新事实，不静默覆盖。响应未知先核对结果，不重复调序或重复建版本。

趣味来自可理解的反馈：船形拖动标识、队列轻轻让位、合法落点发亮、时间条吸附、提交后局部状态自然变化。业务场景区可保留小船与波浪细节；不加满屏漂浮、提示音或庆祝遮挡。短反馈不阻塞下一操作；持续动效可暂停，后台及减少动态效果时停用。小船表示业务对象或方向，不代表AIS实时船位。

## 3. 每页必须有自己的任务与主视图

| 页面 | 用户首先要判断什么 | 主体及必要交互 | 收起或移走什么 |
|---|---|---|---|
| 总览 | 全港当前哪里需要关注 | 既有港口场景与真实跨业务概要；少量重点和模块入口；按角色突出待办 | 单船资料、整张业务清单、重复的十项指标 |
| 进港预约 | 申请内容是否完整，下一步是提交还是审核 | 保留适合检索比较的清单；所选申请资料及办理动作；审核员突出待审核，调度员突出登记与草稿 | 重复船名卡片、所有用户都看得到的无权操作区 |
| 锚地排队 | 哪些船实际在场、谁排在前面、下一步安排什么 | 锚地选择及容量/在场图形，有效队列按顺序呈现，取消但未离锚单列；拖动调序预览影响；所选到访可继续安排泊位 | 全历史长表、每行重复操作说明；不能用无地理依据的布局充当实地地图 |
| 泊位计划 | 哪个泊位何时可用、安排是否适配或冲突 | 横轴为时间、纵轴为泊位；区间长度与时间成比例，点击查版本，拖动形成新安排并确认；可继续打开实际记录 | 同尺寸时间标签冒充排期图，永久展开所有历史版本 |
| 进出港记录 | 当前可记录哪一步，之前实际发生了什么 | 按下一动作组织待办；所选到访的事实时间线；按需切换完整记录查询 | 让用户从全事件长表自行推断下一步；把计划节点画成已发生事实 |
| 查询统计 | 等泊、资源使用、执行偏差是否有变化 | 主图看趋势，辅图做比较/分布；点击有效图形查看同口径明细；筛选与导出一致 | 一屏十个大数字加几张长表，重复图例和不必要的常驻口径段落 |
| 基础资料与账号 | 业务引用能否维护、谁能操作 | 管理员管理入口，按对象分组的标准清单与表单；停用保留引用，受保护代码不可随意修改 | 每个基础表单独扩成一级菜单、无意义装饰图表 |

统一的是外框、字体、颜色、控件含义和反馈；不是每页的列数或内容配比。表格适合精确查询，图像适合场景，图表适合比较；不规定每页必须有照片或固定数量图表。关键字段和操作保持可读，不靠缩小字号塞满屏幕。

## 4. 角色对应任务，而非四套界面

下表是后续交付目标。现有主线只开放总览、预约与认证；不能将本表当作已实现权限。

| 角色 | 优先任务 | 可写操作 | 其他页面 |
|---|---|---|---|
| 调度员 | 登记申请、安排队列和泊位 | 登记/草稿/提交；按规则撤销或申请变更；入离锚、调序；编制/确认/调整/取消计划；允许实际作业登记 | 可查询与职责相关的全港事实；不具备审核权限 |
| 审核员 | 待审核申请与变更后的重审 | 批准、驳回，保留意见和责任人 | 共用查询页面，不显示锚地、计划及作业写入表单 |
| 记录员 | 待登记进港、靠泊、离泊 | 记录事实；更正需走受控流程并保留原因及前后值，具体条件在6C确定 | 查询计划与到访资料；不能审批或更改泊位安排 |
| 管理员 | 基础资料、账号、问题追溯 | 授权范围内跨职责操作及维护 | 共用业务页，不用管理员全权限代替其他角色验收 |

初次登录可突出角色任务，用户已选筛选不得被“智能默认”反复覆盖。无权操作隐藏；有权但状态不符的操作在相关位置说明原因，不堆整页灰按钮。更换账号后清空不再合法的选择和待提交动作，重新读取权限。既有匿名只读范围保持显式，不自行增加租户/船公司隔离；不让匿名访问受控账号维护和审计信息。

同学版确实有服务端角色检查，主要界面差异是按钮显隐；任务优先级和阅读路径尚未充分区分。不能说其完全没有权限，也不能说已有完整角色体验。

静态核对发现：主线审核和预约登记过程已限定业务角色，但 `04_procedures.sql` 中调序、计划和实际事件过程目前仅检查账号与角色启用，尚不足以保证上述细分授权。接入各批写操作前补齐过程权限：队列调序/计划为ADMIN、DISPATCHER，实际入离锚/进港/靠离泊为ADMIN、DISPATCHER、RECORDER；更正与维护按对应批次另定条件并验证。API授权通过不能替代数据库越权测试。

## 5. 统计可视化的用途与来源

| 要回答的问题 | 首选图形 | 数据和必要限制 |
|---|---|---|
| 最近等泊是否变长 | 按日平均已完成等待折线，显示样本量 | 按离锚日归组；多次停留可切换到访累计口径；无样本留空，不补0、不伪造趋势 |
| 各泊位使用情况如何 | 泊位实际占用率横向条形图 | 实际在泊与有效观察区间的交集；截至当前的分母不能包含未来时段；可下钻在泊记录 |
| 靠泊提前或延误多少 | 以0为基线的偏差散点/分布图 | 实际靠泊减固定执行版本计划时间；明确正负方向；点选样本定位到访 |
| 是否按计划靠泊 | 准点率趋势或比例摘要 | 统计期内已靠泊预约为分母；无样本显示无数据，不能显示0%或100%；不预设容差改变报告定义 |

第一批先做好两种能联查的图，下一批再补偏差和准点；不一口气铺满图表。ECharts 按需加载，图形有文本/明细替代，键盘也可查样本；图表点击产生的筛选可见且可清除。船舶、泊位、日期、状态筛选及导出对同一个查询范围生效。

接手者的主要负担：`AppointmentListView.vue` 名字像单页，实际同时承担外框、导航、总览和预约；各说明文件散落当前状态；SQL加载代码在多处重复；CSS后续覆盖需要上下文。4A明确职责，4B接页时再做必要整理：外框使用表达工作台职责的命名（如 `PortWorkspace.vue`），页面内容归各自View，保留筛选/选择与导航语义；SQL加载重复确有第二处新增用途时收拢成一个小函数；按页面归拢样式，不建立万能页面工厂。

清理分三类：已撤下的通用查询不再恢复；无引用依赖/样式先用搜索、构建、截图证明后删除；事务锁、请求序号、缓存、注册重试键和SQL误报设置是有历史原因的保护，不因复杂而删。当前没有源码使用 axios/Element Plus/ECharts，但 ECharts 是统计阶段既定能力；依赖清理应逐项确认，不能一次全删。以上是清理候选，本轮未删任何业务代码。

## 7. 跨领域借鉴与反证

- 借鉴机场地面调度的“实际在场≠待调度”，分别呈现取消待离锚和有效队列；不引入真实航迹。
- 借鉴会议室/手术室预约的资源时间轴，区分草稿、已确认和实际占用；不能因为时间轴看起来空闲就绕过数据库适配与锁。
- 借鉴物流轨迹的事实时间线，计划与实际分开；离泊不是已驶离港界，不伪造模型没有的事实。
- 借鉴财务报表的摘要—明细追溯，同一图表的数必须能追到同批查询样本；不引入财务系统架构。

反证标准：A若让用户反复导航才能完成一步，改跨页衔接；时间轴若在多泊位/窄屏失去可读性，提供日期缩放、资源筛选及等价明细；图表若样本稀少，展示原始样本而不拟合趋势；角色默认若覆盖用户筛选，保留用户意图。拖动若在短屏、长队列或精确时间输入时更难用，应保留明确的等价操作，不能为互动感逼用户拖动。新设计若比旧清单更慢、更难核对，应简化而非用新颖性辩护。

二阶影响是图形选择需要共享对象定位、写入影响其他模块和角色权限变化；三阶影响是缓存分叉、重复状态和测试成本。以明确的失效关系、共用业务契约和最少共享控件控制，不引入工作流引擎、全局事件总线或四份角色状态。具体批次与可观察验收结果见现有计划文件。
